# 基于 STM32F103 的双通道 OTA 远程固件升级系统

## 项目简介

本项目在 STM32F103C8T6 上实现了一套完整的 OTA（Over-The-Air）固件升级方案，包含 **Bootloader** 和 **APP** 两个工程，支持 **本地串口升级** 与 **Wi-Fi远程升级** 两条升级通道：

## 复现流程

1. 烧录Bootloader工程后，在串口软件上用串口1发送**app_ota.bin**文件，推荐使用**XCOM**串口软件，波特率为**115200**，发送成功后程序将跳转去运行APP工程，此时在串口中可见到**本地串口升级成功** ，同时板子上的**红绿灯**会不断闪烁，表达本地串口升级顺利完成
2. 本地升级成功后，程序会开始不断尝试链接网络热点，要连接的热点的名称和密钥皆在APP工程的**net.h**里面，热点需设置为**2.4GHZ**
3. 成功连接上网络后，程序接下来会不断尝试连接TCP服务器，要连接的服务器的 **IP和端口**也在**net.h**，若成功连接串口会发送**“TCP已连接”**，此刻就可以远程发送固件了
4. 注意，如果tcp服务器**发送固件的速度过快**，wifi模块极有可能会在接收固件的时候丢失部分数据，导致远程升级失败，如果没有适合的tcp服务器，推荐使用开源文件中的**send_ota.bat**（记得配套**send_ota.ps1**文件），这是一个wifi发送工具，双击后即可出现一个不断监听的tcp服务器，自带**ACK、断点续传**等功能，同时会将固件已**150ms**的间隔分包发送。该工具会自动向模块发送**app_ota2.bin**文件（电脑与模块需要**连接同一网段**）
5. 程序成功接收到该远程发送的固件后，将会**再次重启**，若串口中每两秒打印一次**远程升级成功** ，同时板子上的**蓝灯**不断闪烁，说明远程升级顺利完成，整个流程成功复现


## 软件架构设计

系统分为 **Bootloader** 和 **APP** 两个独立工程，通过**标志页**（`0x0800FC00`）和 **W25Q64 暂存区**（`0x00010000`，12 个扇区 / 48KB）解耦：

```
              ┌───────────── 串口通道 ─────────────┐
  PC(XCOM) ──USART1──▶ Bootloader ──▶ W25Q64 ──▶ 内部 Flash ──▶ 跳转 APP
              └────────────────────────────────────┘

              ┌───────────── Wi-Fi 通道 ────────────┐
  PC ──TCP──▶ ESP8266 ──USART3──▶ APP ──▶ W25Q64 ──▶ 写标志 ──▶ 复位
                                                              │
                                        Bootloader 只负责搬运 ◀┘
              └────────────────────────────────────┘
```

### Bootloader（20KB @ `0x08000000`）
| 层 | 职责 |
|---|---|
| 接收层 | USART1 + DMA1_CH5 **循环模式** + 2KB 环形缓冲，靠 `CNDTR` 差分取数据 |
| 校验层 | 包头 `OTA1` / 长度 / CRC32 / 固件头（SP、PC 合法性） |
| 搬运层 | W25Q64 → 内部 Flash，每次 256 字节，搬完再算一遍 CRC 复核 |
| 跳转层 | 关中断、关 SysTick、清 NVIC、关外设、重定位向量表、换栈后跳转 |

### APP（40KB @ `0x08005000`）
| 模块 | 职责 |
|---|---|
| `esp8266.c` | AT 指令驱动：复位、连热点、连 TCP、透传；**AT 阶段用 IT 接收，OTA 阶段切循环 DMA** |
| `net.c` | OTA 协议：`READY` / `CHUNK` / `ACK` / `OK FLASHING`，断点续传与 CRC 复核 |
| `main.c` | 启动、时钟继承、主循环（重连 + 收包 + 闪灯 + 版本提示） |

### 升级包格式
```
+--------+---------+---------+------------------+
| "OTA1" |  长度   |  CRC32  |   固件数据        |
| 4 字节 |  4 字节 |  4 字节 |      N 字节       |
+--------+---------+---------+------------------+
CRC32：多项式 0xEDB88320，初值/结果异或 0xFFFFFFFF（与 zlib.crc32 一致）
```

### Wi-Fi OTA 协议（板子为偏移量的唯一权威）
```
板子 → 电脑 : READY <已写入字节数>
电脑 → 板子 : CHUNK <偏移> <长度>\r\n + 原始数据
板子 → 电脑 : ACK <新的已写入字节数>
板子 → 电脑 : OK FLASHING        （收满且 CRC 校验通过）
板子 → 电脑 : ERR HEAD/CRC/LEN/OFFSET
```
# 程序运行流程

## 一、Bootloader工程：上电与接收

1. 在一开始把 Bootloader 工程烧录到板子里面后，`main` 程序里面先检测 APP 是否有升级标志。若没有，则去 APP 工程的地址读取向量表；若检测到 RAM 不正常，则说明 APP 工程还没有被烧录进来，则会在串口里面发送 `[BOOT] APP 区为空`，并进入固件接收模式，等待接收固件，同时擦除外部 flash 模块存放固件的扇区。最后在 `while(1)` 里面的 `OTA_Task()` 不断主动轮询，会每两秒检测串口里面是否有数据发送。
2. 在串口中发送数据后，程序会先把 DMA 收到的新数据搬进环形缓冲中，然后再把环形缓冲里的数据分批写进外部 flash 中。写入完毕后，程序会开始读取 flash 内的数据来进行检查。
3. 在检查期间，若出现字节丢失和数据量过少的情况都会升级失败并返回。如果前面的情况都没有，程序会查看包头内的前四个字节是否有 `OTA1`，检查固件长度是否为 0，或者是否超出 APP 区的最大容量，最后将外部 flash 内的数据算一遍 CRC 码，然后将算出来的 CRC 码和包头自带的 CRC 码进行比较，检查固件在传输前和传输后的数据是否一致。每个检查程序在检测不通过后都会触发升级失败；每次触发升级失败并返回后，都会再擦除一次 flash 模块并再次进入接收模式，擦除完成之后才打印 `请重新发送固件`。
4. 最终，程序检查 SP 和 PC 是否正常。若通过了所有的检查程序，程序会将魔数、固件长度、CRC 码、包头长度写进内部 flash 存放升级标志区域中，并开始软复位。
   
## 二、Bootloader工程：搬运与跳转

5. 程序复位后，`main` 程序会再次检测 APP 区是否有升级标志，也就是魔数。成功在 APP 区检测到正确的魔数后，将开始程序升级流程。
6. 在程序升级流程中，程序会去内部 flash 存放升级标志区域中读取数据，随后也会检查一遍升级标志、固件长度、包头长度（数据偏移量）。检查通过后会擦除内部 flash 的 APP 区，然后正式开始把外部 flash 中的固件传输到内部 flash 中。搬运方式也为分批搬运，每次最多搬运 256 个字节，防止搬运速度过快导致出现错误。
8. 搬运完毕后，比对一下内部和外部 flash 里面固件的 CRC 码，确认一致后正式开始跳转到 APP 区的流程。
9. 在开始跳转到 APP 区的流程中，程序会检查一遍 SP 和 PC 是否合理，随后检测 APP 区的空白占比，若空白占比没有大于 70%，则表示一切正常。然后在正式跳转前停 DMA 和断开串口 DMA 请求，关掉 SPI1，关闭总中断，关闭所有外部中断权限，清除所有中断标志，接着将向量表偏移量设置为 APP 的基地址，再设置堆栈指针（已同步数据/指令屏障），最后用 `((pFunction)pc)()`，让函数指针跳转到 APP 的复位处理程序中。

## 三、APP 工程：联网与协议

1. 成功跳转到 APP 工程之后，用 `SCB->VTOR = 0x08005000` 来让中断向量的起始位置指向 APP 工程的初始位置，随后开启总中断，让程序正式开始运行 APP 工程的程序。在连接网络前会在串口发送 `[APP] 启动`，在之后板子上的红绿灯将开始闪烁，并且每隔两秒打印一次 `本地串口升级成功`。
2. 本地串口升级成功后，程序会第一时间调用 `ESP8266_Task()` 来启动 WiFi 连接程序。若 WiFi 或 TCP 服务器连接失败，则会退出来进入 `while` 循环，开始每三秒尝试一次连接 WiFi 和 TCP 服务器。
3. APP 工程的串口 3 有两种模式，一个是 IT 中断模式，一个是 DMA 循环模式。在一开始的网络连接中先使用 IT 中断模式，用来给 WiFi 模块发送指令。首先是给 WiFi 模块发 AT 查看 WiFi 模块是否正常，然后设置为 STA 接收模式，再然后设置为单连接模式；前面的工作做好之后就开始连接 WiFi 热点，WiFi 连接成功后，就开始尝试连接 TCP 服务器。若两者都连接成功，则随之设置为透传模式，然后再让 WiFi 模块进入发送模式。对 WiFi 模块的工作做好之后就开始擦除外部 flash 模块中存放固件的扇区，擦完后就让串口的中断模式改为 DMA 循环模式，随后清除接收缓冲区中的垃圾数据，并向服务器发送 `READY`，表示 WiFi 模块已经可以开始接收固件了。
4. 此时正在监听的TCP服务器收到 `READY` 后开始按协议发包：先发一行 `CHUNK <偏移> <长度>`，紧接着发这一包的原始数据。板子在 DMA 循环模式里把收到的字节逐个拼成命令行，遇到换行符就立刻解析：长度必须在 1~512 字节之间；**偏移必须等于板子已经写入的字节数**，不一致就回 `ERR OFFSET <板子真实偏移>` 让电脑自己纠正；如果一致，则进入"等这一包数据"的状态。
5. 等这一包的字节全部到齐后，程序开始把数据取出来，写到外部 flash 的 `0x00010000 + 已写入字节数` 位置，写完后回 `ACK <新的已写入字节数>`。**每写完一包都会检查是否收满**：够 12 字节就解析一次包头（`OTA1`、固件长度），包头不对或长度异常就回 `ERR HEAD` / `ERR LEN`，擦除暂存区并回 `READY 0` 从头再来。
6. 当已写入字节数等于 `12 + 固件长度` 时，程序对**外部 flash 里实际存的数据**重新算一遍 CRC32，和包头里的 CRC 比对：不一致就回 `ERR CRC`，擦除后重新开始；一致才回 `OK FLASHING`，然后把 `{魔数 0xAABB1122, 固件长度, CRC 码, 偏移 12}` 写进内部 flash 的升级标志页（`0x0800FC00`），延时 200ms 后执行 `NVIC_SystemReset()`。
   
## 四、APP 工程：联网与协议

7. 整个收包过程有两道超时保护：**某一包数据超过 1.5 秒还没到齐**，或**连续 5 秒没有收到任何命令**，都会判定链路已经断开，接着就会返回主循环，3 秒后重新调用 `ESP8266_Task()` 再重新走一遍流程。
8. 重连时有一个关键细节：**暂存区只在第一轮擦除**（靠 `erased` 标志判断），断线续传时绝不擦，否则前面收的全没了。重连成功后板子会再发一次 `READY <已写入字节数>`，电脑从板子报的偏移继续发 —— 这就是**断点续传**，不重发、不跳过。
9. 复位之后回到 Bootloader，此时升级标志页里已经有正确的魔数，Bootloader 就会再进行一次本地升级，再次跳转到APP工程后，整个升级闭环完成。

## 注意事项

1. 使用该 wifi 发送工具的原因，是因为受限 esp8266 模块，**过快的发送速度和网络不稳定**都会导致远程升级失败。若有更好的硬件条件和性能更高的 wifi 模块，或许可以直接使用手机上的“网络调试工具”软件来创建 tcp 服务器直接发送固件。
2. 仓库里有两个固件，一个是 **app_ota.bin**，一个是 **app_ota2.bin**：
   - **app_ota.bin**：由 APP 工程生成的固件，功能有让板子的**红绿灯闪烁**和**连接网络来远程升级**，用于本地串口升级来为后面的远程升级做铺垫。
   - **app_ota2.bin**：仅会让板子的**蓝灯闪烁**，**没有远程升级的功能**，仅用来演示远程升级成功，若想再次验证，则需重新烧录 **app_ota.bin**。
3. APP 分支里面的 **make_ota.exe** 是用于给固件加上包头的脚本。在 APP 工程里面点击 **Rebuild** 后，可会用新的 **app_ota.bin** 覆盖原本的 bin 文件，**app_ota2.bin 不受影响**。
4. 在程序运行期间用本地串口发送 **“OTA”** 后，可使程序重新进入固件接收模式。

## 排错记录

## 一、时钟继承问题

### 1. 现象

进行本地串口升级后，程序无法实现 APP 工程的功能，无论是打印还是闪烁 LED 都不行，像是跳过去之后就死机了；而如果单独将 APP 工程烧录进板子，却可以正常运行。

### 2. 排查过程

APP 工程单独烧录可以正常运行，那么就可以得知问题出在**双工程升级**中。所以我在 APP 工程的每句初始化后面都加入了探针，示例为：

```c
int main(void)
{
  OTA_PROBE('1');                 //收到 1 = 跳转成功，已经进 main 了
  SCB->VTOR = 0x08005000;

  NVIC_ClearPendingIRQ(USART1_IRQn);
  NVIC_ClearPendingIRQ(USART3_IRQn);

  HAL_Init();
  OTA_PROBE('2');                 //HAL 初始化完成
  __enable_irq();                 //尽早开总中断

  SystemClock_Config();
  OTA_PROBE('3');                 //时钟就绪

  MX_GPIO_Init();
  OTA_PROBE('4');                 //GPIO 完成
  MX_DMA_Init();
  MX_SPI1_Init();
  MX_USART1_UART_Init();
  OTA_PROBE('5');                 //USART1 重新初始化完成
  MX_USART3_UART_Init();
  OTA_PROBE('6');                 //所有外设初始化完成

  OTA_PROBE('7');                 //进主循环，灯该闪了
  while (1)
  {
      //纯寄存器闪灯：不依赖 HAL_Delay / SysTick
      GPIOA->BRR  = GPIO_PIN_1;
      for (volatile uint32_t i = 0; i < 400000U; i++) { }
      GPIOA->BSRR = GPIO_PIN_1;
      for (volatile uint32_t i = 0; i < 400000U; i++) { }
  }
}
```

加入探针后，串口日志中打印出了 **`12`**，这证明程序卡死在了**时钟初始化阶段**。所以我找到了初始化时钟的代码，也分别加入了探针，示例如下：

```c
if ((RCC->CFGR & RCC_CFGR_SWS) == RCC_CFGR_SWS_PLL)
{
    SystemCoreClock = 72000000U;      //Bootloader 已配好
    OTA_PROBE('C');                   //C = 继承 72MHz，走这条就对了
    return;
}

for (retry = 0U; retry < 3U; retry++)
{
    if (HAL_RCC_OscConfig(&RCC_OscInitStruct) == HAL_OK) break;
    HAL_Delay(10);
}
if (retry >= 3U)
{
    OTA_PROBE('E');                   //E = HSE/PLL 起不来
    Error_Handler();
}
...
if (HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_2) != HAL_OK)
{
    OTA_PROBE('F');                   //F = 切到 PLL 失败
    Error_Handler();
}
```

加入探针后，现象是串口中打印出了 **`E`**，这证明在程序初始化期间 `HAL_RCC_OscConfig()` 失败。去 `stm32f1xx_hal_rcc.c` 里面翻找该函数后，才知道在跳转前 Bootloader 已经把 PLL 当系统时钟了，而到了 APP 工程还想"重新配 HSE + PLL"，这直接导致了 HAL 直接拒绝，随后触发了 `Error_Handler()`，所以才出现了类似于死机的死循环。

### 3. 解决

在 `SystemClock_Config()` 里面的初始化代码前面添加上了 `if` 语句：如果程序是从 Bootloader 跳过来的，则会触发这个 `if` 语句，将主频统一为 72MHz，然后返回，不去理会后面的时钟初始化代码，防止触发 `Error_Handler()`；若为单独烧录的冷启动，则不会触发这个 `if`，继续执行后面的时钟初始化代码。

### 4. 复盘

系统时钟只能初始化一次，一旦多次初始化就会触发错误，所以像 OTA 这种程序升级的项目中，要避免 APP 工程再次给时钟进行初始化。

## 二、DMA 每次重开都会丢几微秒的数据

### 1. 现象

发送 12884 字节的固件，收完校验时报错：

```
实际传输数据大小和固件大小不一致，升级失败
实际传输大小为 12764，应传输 12884
```

每次都**稳定少 120 字节**；包头没有问题，但是长度就是对不上。

## 二、DMA 每次重开都会丢几微秒的数据

### 1. 现象

发送 12884 字节的固件，收完校验时报错：

```
实际传输数据大小和固件大小不一致，升级失败
实际传输大小为 12764，应传输 12884
```

稳定少 **120 字节**，而且每次都是这个数；包头完好，只是长度对不上。

### 2. 排查过程

当时代码已经用的是 DMA 接收，先按"三个计数器"逐个排除：

| 计数器 | 含义 | 当时的值 | 说明 |
|---|---|---|---|
| `lost` | 环形缓冲满了丢的字节 | **0** | 不是缓冲区不够 |
| `uart_err` | 串口错误回调次数 | **0** | 不是溢出、不是干扰 |
| `rx_total` | 总共收进 MCU 的字节 | **12764** | 和 `staged` 一致 → 数据根本没有进来 |

三个都是"正常"的，但总数就是少了 120，说明**字节在进入 MCU 之前就消失了**，和缓冲没有关系。

**然后我计算了一下**：

```
1. 12884 字节 ÷ 512 字节/包 ≈ 25 次接收
2. 120 字节 ÷ 25 次 ≈ 4.8 字节/次
3. 115200 波特率下，1 字节 ≈ 87µs
4. 4.8 字节 ≈ 420µs
```

这意味着**每次接收结束都恰好丢 4~5 个字节，约 420µs 的量**，这正好是"HAL 停掉 DMA 后，经过回调再重新启动 DMA"这段开销。

所以我去查看了对应的代码：

```c
void HAL_UARTEx_RxEventCallback(UART_HandleTypeDef *huart, uint16_t Size)
{
    if (huart->Instance != USART1) return;
    if (Size > RX_DMA_SIZE) Size = RX_DMA_SIZE;

    ring_push(rx_dma, Size);                                    //搬进环形缓冲

    //重新开接收（HAL 在回调前已经把状态置为 READY，可以再次启动）
    HAL_UARTEx_ReceiveToIdle_DMA(&huart1, rx_dma, RX_DMA_SIZE); //问题在这里！
    __HAL_DMA_DISABLE_IT(&hdma_usart1_rx, DMA_IT_HT);
}
```

`HAL_UARTEx_ReceiveToIdle_DMA()` 是**普通模式**：收满或空闲一次，DMA 就停了，系统必须在回调里重新启动。而**从"停"到"重新启动"之间到达的字节，没有 DMA 在接收，会直接丢掉**。

### 3. 解决

直接改成循环 DMA，启动一次永不停，防止漏掉字节：

```c
static void uart_rx_start(void)
{
    hdma_usart1_rx.Instance       = DMA1_Channel5;          //F103 上 USART1_RX 固定是通道5
    hdma_usart1_rx.Init.Direction = DMA_PERIPH_TO_MEMORY;
    hdma_usart1_rx.Init.MemInc    = DMA_MINC_ENABLE;
    hdma_usart1_rx.Init.Mode      = DMA_CIRCULAR;           //★ 循环模式：搬到底自动回到开头
    HAL_DMA_Init(&hdma_usart1_rx);

    HAL_DMA_Start(&hdma_usart1_rx,
                  (uint32_t)&huart1.Instance->DR,
                  (uint32_t)rx_dma, RX_DMA_SIZE);

    SET_BIT(huart1.Instance->CR3, USART_CR3_DMAR);           //让串口把数据交给 DMA
}
```

现在主循环侧不再靠回调，而是**读计数器**算出 DMA 搬到哪了：

```c
static void dma_to_ring(void)
{
    //已经搬了多少 = 总量 - 剩余量（CNDTR 从 2048 往下减）
    head  = RX_DMA_SIZE - __HAL_DMA_GET_COUNTER(&hdma_usart1_rx);
    count = (head - rx_tail) & RX_DMA_MASK;      //记录这一圈里新增了多少

    ring_push(&rx_dma[rx_tail], count);          //搬进环形缓冲中
    rx_tail = (rx_tail + count) & RX_DMA_MASK;
}
```

**循环模式和普通模式关键差别在于**：循环模式下 DMA 永远在转，**不存在"停-开"这个动作**，也就没有那 420µs 的空窗，所以也不会丢失字节。

### 4. 复盘

丢字节不是"传坏了"，而是**接收逻辑自己制造的空窗** —— 普通模式 DMA 每次收完就停，重开那几百微秒里到达的字节没人接，120 ÷ 25 ≈ 4.8 字节正好对应 115200 下约 420µs 的重开开销，数字完全吻合；**只要涉及"停-开"DMA，中间就一定有窗口期，能用循环模式就别重开**，主循环用 `CNDTR` 差分取数据，代码反而更简单。

## 三、包头不是 OTA1：模块把 AT 指令回显也发回来了

### 1. 现象

Wi-Fi 传输能跑到 100%，但板子校验时报**包头不是 `OTA1`**，升级失败。加了诊断打印之后，串口打出：

```
>>> 包头不是 OTA1，Flash 前 16 字节: 41 54 2B 43 49 50 53 54 41 52 54 0D 0A  (已收 21 字节)
```

把这串十六进制翻译一下：

```
41 54 2B 43 49 50 53 54 41 52 54 0D 0A
 A  T  +  C  I  P  S  T  A  R  T  CR LF
```

**就是字符串 `"AT+CIPSTART\r\n"`**，也就是我们自己刚刚发出去的那条指令。

### 2. 排查过程

这已经是"包头不是 OTA1"的**第三次**了。第一次是写 Flash 之前没有擦扇区，写进去是乱码；第二次是写 Flash 的那几毫秒里，接收缓冲被下一批数据覆盖；第三次加了"打印第一块内容"的诊断，才看到真相。

**关键的一步是：不要只打印"包头不对"，而是把读回来的前 16 个字节打成十六进制。**

```c
/* 调试：打印第一块的长度和前 16 字节，看看到底收到了什么 */
if (app_ota_staged == 0)
{
    int k;
    printf(">>> 第一块 %u 字节: ", (unsigned)ESP_RxSize);
    for (k = 0; (k < 16) && (k < ESP_RxSize); k++) printf("%02X ", ota_buf[k]);
    printf("\r\n");
}
```

看到 `41 54 2B 43 ...` 之后一眼就能认出来是 `AT+`：**ESP8266 默认回显 AT 指令**，透传模式下这些回显字节和固件数据混在同一条串口流里，被当成固件存进了最前面，导致整个固件**后移 21 字节**，包头自然不是 `OTA1`。

### 3. 解决

加一个"重同步"机制：收到数据时先找 `"OTA1"` 四个字节，**找到之前的内容全部丢弃**，找到之后才从那里开始存。

```c
/* 在数据里找包头，找到之前的数据全部丢掉 */
if (app_ota_staged == 0)
{
    int i, found = -1;

    for (i = 0; i + 4 <= (int)ESP_RxSize; i++)
    {
        if ((ota_buf[i] == 'O') && (ota_buf[i+1] == 'T') &&
            (ota_buf[i+2] == 'A') && (ota_buf[i+3] == '1'))
        {
            found = i;
            break;
        }
    }

    if (found < 0) return;                  //这一块里没有包头，整块丢掉
    if (found > 0)                          //前面有垃圾，往前挪
    {
        memmove(ota_buf, ota_buf + found, ESP_RxSize - found);
        ESP_RxSize = (uint16_t)(ESP_RxSize - found);
    }
}
```

这样不管模块在前面夹带了多少回显、URC、启动乱码，都能自动跳过。

### 4. 复盘

"包头不对"不等于"数据传坏了"，不要只报一句失败，要**把实际收到的字节打成十六进制**，`41 54 2B 43` 这种一眼就能看出是 `AT+`；根因是 ESP8266 默认回显 AT 指令，回显和固件数据混在同一条串口流里被一起写进了 Flash，所以**只要数据源是"模块转发的串口流"，那么就要假设它可能夹带杂质**，用"找到 `OTA1` 再开始存"的重同步方式兜住，而不是假设收到的第一个字节就是数据。

## 四、字节数对、长度对，但 CRC 就是不对

### 1. 现象

传输完成，字节总数完全正确（15484），但校验不过，三个CRC都对不上：

```
CRC: 包头=0xC8A896B0  W25Q64=0xE367E2A2  内部Flash=0xE367E2A2
```

不难注意到，后面两个是相同的。

### 2. 排查过程

要先看先看"谁和谁相等"，把范围缩小：

1. W25Q64 的 CRC 和内部 Flash 的 CRC 完全一致，说明 Bootloader 的搬运过程是对的，内部 Flash 也没问题。
2. 已收字节数完全正确（15484），说明不是丢包。
3. 两条合起来：数据在写进 W25Q64 之前就已经被改过了，问题出在**接收环节**。

顺着接收链路往下看：串口中断回调 → 共享缓冲 `ESP8266_RxBuff` → 主循环拷贝 → 写 Flash。问题就在回调里：

```c
else if (huart->Instance == USART3)
{
    ESP_RxSize = Size;
    ESP_RX_Complete = 1;

    //重新开启 ESP8266 接收
    HAL_UARTEx_ReceiveToIdle_IT(&huart3, ESP8266_RxBuff, UART_RX_BUFF_LEN);   //问题在这里！
}
```

回调把数据放进缓冲后立刻重开接收，而主循环这时还在读这块缓冲准备写Flash（写 512 字节要 3~6ms），新数据马上就从 `ESP8266_RxBuff[0]` 开始覆盖，于是存进 Flash 的是**半新半旧的混合数据**。

所以原因是：**总字节数完全正确，只有内容错了**，而内容对不对，需要算一遍CRC才行。

### 3. 解决

把"重开接收"从回调里挪到主循环，并且要在"搬运数据之后"再重开：

```c
uint16_t n = ESP_RxSize;
if (n > UART_RX_BUFF_LEN) n = UART_RX_BUFF_LEN;

memcpy(ota_buf, ESP8266_RxBuff, n);     //先搬运私有缓冲，只要几微秒
ESP_RxSize = n;

//数据已经搬走，现在可以安全地重新开接收了
if (HAL_UARTEx_ReceiveToIdle_IT(&huart3, ESP8266_RxBuff, UART_RX_BUFF_LEN) != HAL_OK)
{
    HAL_UART_AbortReceive(&huart3);
    HAL_UARTEx_ReceiveToIdle_IT(&huart3, ESP8266_RxBuff, UART_RX_BUFF_LEN);
}

SPI_FLASH_WriteBuffer(0x00010000 + app_ota_staged, ota_buf, n);   //再慢慢写 Flash
```

后来接收方式换成DMA循环模式之后，这段逻辑更彻底地消失了：DMA 把数据搬进独立的圆圈，主循环从圆圈里取，根本不存在"回调和主循环抢同一块缓冲"的问题。

### 4. 复盘

需要看三个CRC谁和谁相等，W25Q64 和内部 Flash 一致说明搬运没问题，那就可以直接将排查范围从两条链路缩小到接收这一环；根本原因就是共享缓冲区的同时访问，回调里重开接收之后，主循环还没读完、新数据就开始写了，所以**共享缓冲的原则永远是先搬运数据，再写flash"**，搬运只要几微秒，而写Flash的几毫秒绝对不能占用这块缓冲区。

## 五、只收到 512 字节：看门狗计数器没清零

### 1. 现象

这是最折磨我的问题，Wi-Fi 传输稳定地停在 **512 字节**，每次重连都停在同一位置，看起来像"模块发了 512 字节就不发了"。串口每轮都打印：

```
[NET] 接收中断：已收 512 / 14868 字节
[NET] 清空暂存区，重新连接服务器...
```

从手机热点里还能看到WiFi模块一两秒断一次，因为每轮重连都会硬复位模块。

### 2. 排查过程

一开始怀疑模块或者硬件问题，换杜邦线、换充电宝给电脑或者给板子供电、降低波特率、改善网络环境，全都试过，问题始终没有解决

后来加上了计数器打印，发现**每一轮都精确停在 512**，这就很不像硬件问题了：如果是真丢包，不可能每次都正好丢到同一个字节。而且512正好是一个HAL缓冲的长度，说明程序不是"收不到"，而是"收完第一包就判定了失败"

所以回头看超时判断那一段，我找到两个关键代码

第一段代码，计时只在"数据有增长"时才会刷新：

```c
/* 数据有增长就刷新计时，用来发现"卡住" */
if (app_ota_staged != ota_last_staged)
{
    ota_last_staged = app_ota_staged;
    ota_last_tick   = HAL_GetTick();
}
```

第二段代码，超时分支直接把 `app_ota_staged` 清零了，却没有清 `ota_last_staged`：

```c
if (ota_head_ok && (app_ota_staged < (12 + ota_len)) &&
    (HAL_GetTick() - ota_last_tick > 5000))
{
    printf("[NET] 接收中断：已收 %u / %u 字节\r\n",
           (unsigned)app_ota_staged, (unsigned)(12 + ota_len));

    app_ota_staged = 0;
    ota_head_ok    = 0;
    ota_len        = 0;
    ota_crc        = 0;
    ota_erased     = 0;
    /* 这里少了一句 ota_last_staged = 0; */

    is_network_ready = 0;
    return;
}
```

于是下一轮出事：

```
上一轮结束时：app_ota_staged = 0，ota_last_staged = 512
新一轮第一包到达：app_ota_staged = 512
判断 app_ota_staged != ota_last_staged 结果为假，时间戳不刷新
超时判断用的是上一轮留下的旧时间戳，早就超过 5000ms
立刻打印"已收 512"，再清空、再重连，无限循环
```

**第一次失败是真的传输问题，从这个bug生效开始，后面每一轮都被判定为失败"**，串口日志中的现象被伪装成"模块每次都稳定地只发 512 字节"，这无疑是肥美的

### 3. 解决

在超时分支里补一句：

```c
app_ota_staged  = 0;
ota_last_staged = 0;      // ← 补这一句
ota_head_ok     = 0;
```

补上该计数器的清除后，程序终于正常运行，之后的数据搬运不再会判定为失败

### 4. 复盘

该现象太像硬件问题，每轮都停在同一个字节上，很容易让人认为是"模块坏了"，但**硬件故障是随机的，软件bug才是这么整齐的**；真正的原因是超时分支只清了一半状态、漏了一个计数器，导致一次失败被放大成永远失败，所以**凡是关于"超时重置"的程序，要把和这次传输相关的状态全部清干净**，包括那些只是"用来比较"的变量，而不是只清主计数器。

## 硬件与工具链

- **MCU**：STM32F103C8T6（Cortex-M3，64KB Flash / 20KB RAM，HSE 8MHz × 9 = 72MHz）
- **外部 Flash**：W25Q64（SPI），12 个扇区做固件暂存
- **Wi-Fi**：ESP8266（AT 指令，USART3，115200）
- **开发环境**：Keil MDK（ARMCC 5.06）
- **自制工具**：
  - `make_ota.exe`：用 C 重写的打包工具（替代 Python 脚本），输出与 `zlib.crc32` 完全一致，已用 SHA256 逐字节比对；“**编译后自动打包**”挂在 Keil 的 After-Build 里。
  - `send_ota.ps1`：电脑端 Wi-Fi 发送工具，实现停等 ACK、断点续传、端口占用自检。
