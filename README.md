# 基于 STM32F103 的双通道 OTA 远程固件升级系统

## 项目简介

本项目在 STM32F103C8T6 上实现了一套完整的 OTA（Over-The-Air）固件升级方案，包含 **Bootloader** 和 **APP** 两个工程，支持 **本地串口升级** 与 **Wi-Fi远程升级** 两条升级通道：

## 复现流程

1. 烧录Bootloader工程后，在串口软件上用串口1发送**app_ota.bin**文件，推荐使用**XCOM**串口软件，波特率为**115200**，发送成功后程序将跳转去运行APP工程，此时在串口中可见到**本地串口升级成功** ，同时板子上的**红绿灯**会不断闪烁，表达本地串口升级顺利完成
2. 本地升级成功后，程序会开始不断尝试链接网络热点，要连接的热点的名称和密钥皆在APP工程的**net.h**里面，热点需设置为**2.4GHZ**
3. 成功连接上网络后，程序接下来会不断尝试连接TCP服务器，要连接的服务器的 **IP和端口**也在**net.h**，若成功连接串口会发送**“TCP已连接”**，此刻就可以远程发送固件了
4. 注意，如果tcp服务器**发送固件的速度过快**，wifi模块极有可能会在接收固件的时候丢失部分数据，导致远程升级失败，如果没有适合的tcp服务器，推荐使用开源文件中的**send_ota.bat**（记得配套**send_ota.ps1**文件），这是一个wifi发送工具，双击后即可出现一个不断监听的tcp服务器，自带**ACK、断点续传**等功能，同时会将固件已**150ms**的间隔分包发送。该工具会自动向模块发送**app_ota2.bin**文件（电脑与模块需要**连接同一网段**）
5. 程序成功接收到该远程发送的固件后，将会**再次重启**，若串口中每两秒打印一次**远程升级成功** ，同时板子上的**蓝灯**不断闪烁，说明远程升级顺利完成，整个流程成功复现


## 软件架构设计

系统分为 **Bootloader** 和 **APP** 两个独立工程，通过**标志页**（`0x0800FC00`）和 **W25Q64 暂存区**（`0x00010000`，12 个扇区 / 48KB）解耦：

```
              ┌───────────── 串口通道 ─────────────┐
  PC(XCOM) ──USART1──▶ Bootloader ──▶ W25Q64 ──▶ 内部 Flash ──▶ 跳转 APP
              └────────────────────────────────────┘

              ┌───────────── Wi-Fi 通道 ────────────┐
  PC ──TCP──▶ ESP8266 ──USART3──▶ APP ──▶ W25Q64 ──▶ 写标志 ──▶ 复位
                                                              │
                                        Bootloader 只负责搬运 ◀┘
              └────────────────────────────────────┘
```

### Bootloader（20KB @ `0x08000000`）
| 层 | 职责 |
|---|---|
| 接收层 | USART1 + DMA1_CH5 **循环模式** + 2KB 环形缓冲，靠 `CNDTR` 差分取数据 |
| 校验层 | 包头 `OTA1` / 长度 / CRC32 / 固件头（SP、PC 合法性） |
| 搬运层 | W25Q64 → 内部 Flash，每次 256 字节，搬完再算一遍 CRC 复核 |
| 跳转层 | 关中断、关 SysTick、清 NVIC、关外设、重定位向量表、换栈后跳转 |

### APP（40KB @ `0x08005000`）
| 模块 | 职责 |
|---|---|
| `esp8266.c` | AT 指令驱动：复位、连热点、连 TCP、透传；**AT 阶段用 IT 接收，OTA 阶段切循环 DMA** |
| `net.c` | OTA 协议：`READY` / `CHUNK` / `ACK` / `OK FLASHING`，断点续传与 CRC 复核 |
| `main.c` | 启动、时钟继承、主循环（重连 + 收包 + 闪灯 + 版本提示） |

### 升级包格式
```
+--------+---------+---------+------------------+
| "OTA1" |  长度   |  CRC32  |   固件数据        |
| 4 字节 |  4 字节 |  4 字节 |      N 字节       |
+--------+---------+---------+------------------+
CRC32：多项式 0xEDB88320，初值/结果异或 0xFFFFFFFF（与 zlib.crc32 一致）
```

### Wi-Fi OTA 协议（板子为偏移量的唯一权威）
```
板子 → 电脑 : READY <已写入字节数>
电脑 → 板子 : CHUNK <偏移> <长度>\r\n + 原始数据
板子 → 电脑 : ACK <新的已写入字节数>
板子 → 电脑 : OK FLASHING        （收满且 CRC 校验通过）
板子 → 电脑 : ERR HEAD/CRC/LEN/OFFSET
```

## 核心难点与踩坑复盘 (Engineering Highlights)

### 1. 从 Bootloader 继承时钟的两个坑
- **现象**：从 Bootloader 跳过去，APP 直接卡死；DAP 单独烧 APP 却一切正常。后面又出现"Wi-Fi 连接像抽奖，十次有九次 `模块无响应`"。
- **排查推导**：
  - 第一个坑：Bootloader 已经把系统时钟配成 72MHz PLL，APP 再调 `HAL_RCC_OscConfig()` 会被 HAL 拒绝，直接进 `Error_Handler`。
  - 第二个坑更隐蔽：APP 判断"时钟已是 PLL"就只改了 `SystemCoreClock = 72000000` 这个**变量**然后 `return`，但 **SysTick 还按 8MHz 配着**（`HAL_Init()` 时配的 8000 拍）→ `HAL_GetTick()` 快了 **9 倍** → 所有延时和超时跟着缩水 9 倍：5 秒的超时实际只有 555ms，模块还没回话就被判失败。
- **解决**：先判断 `(RCC->CFGR & RCC_CFGR_SWS) == RCC_CFGR_SWS_PLL`，是就直接继承并**补一句 `HAL_InitTick(TICK_INT_PRIORITY);`** 重新配置 SysTick。
- **复盘总结**：`<<< 本地串口升级成功 >>>` 本来该 2 秒一条，结果刷成 1 秒 3 条 —— **这行提示本身就是时钟不对的免费指示器**。以后看到"所有超时都变短"，先查 SysTick 重装载值。

### 2. DMA 每次重开都会丢几微秒的数据
- **现象**：12884 字节的固件，`rx_total` 稳定少 **120 字节**，包头完好但长度对不上。
- **排查推导**：原来是"收满 512 字节 → DMA 停 → 重新启动"，而**重启的那几微秒里到达的字节就丢了**；12KB 需要重启 25 次，25 × 约 5 字节 ≈ 120 字节，数字完全对得上。
- **解决**：DMA 改成**循环模式（CIRCULAR）**，启动一次永不停；主循环用 `CNDTR` 计数器算出"DMA 搬到哪了"，把新数据取走即可。
- **复盘总结**：只要涉及"停-开"的 DMA，中间就一定有窗口期。能循环就别重开。

### 3. 包头变成 `AT+CIPSTART`：模块回显污染了固件
- **现象**：Flash 前 21 个字节是 `41 54 2B 43 49 50 53 54 41 52 54 0D 0A` —— 正是字符串 `"AT+CIPSTART\r\n"`，整个固件被后移 21 字节，包头自然不是 `OTA1`。
- **排查推导**：一开始怀疑丢包，但字节总数是对的；把前 12 字节打出来才发现是 AT 指令的回显 —— **ESP8266 会把指令回显也发回给单片机**，透传模式下这些字节和固件数据混在一条流里。
- **解决**：接收时先找 `"OTA1"` 四个字节，找到之前的内容全部丢弃，找到之后从那里开始存，相当于加了一个"重同步"机制。
- **复盘总结**：只要数据源是"模块转发的串口流"，就默认它可能夹带杂质，不能假设第一个字节就是数据。

### 4. 字节数对、长度对，CRC 就是不对：缓冲区被下一批覆盖
- **现象**：`staged = 15484` 完全正确，但 `CRC: 包头=0xC8A896B0  W25Q64=0xE367E2A2  内部Flash=0xE367E2A2`。
- **排查推导**：先加了三个 CRC 对比打印才看清——**W25Q64 和内部 Flash 完全一致**，说明搬运没问题，坏在接收；字节总数又完全正确，说明不是丢包，而是**内容被改**。最后定位到 `HAL_UARTEx_RxEventCallback` 里立刻重开了接收：新数据马上从 `RxBuff[0]` 开始写，而主循环此刻还在读这块 buffer 准备写 Flash，存进去的是"半新半旧"的混合数据。
- **解决**：回调里只置标志、不重开接收；主循环先 `memcpy` 到私有缓冲（几微秒），再重开接收，最后才慢慢写 Flash。
- **复盘总结**：**"长度正确"不等于"内容正确"**。端到端必须有 CRC，而且校验要分段打印，否则你只知道"坏了"，不知道坏在哪一段。

### 5. 永远只收到 512 字节？看门狗计数器没清零
- **现象**：Wi-Fi 传输稳定地停在 **512 字节**（正好一个 HAL 缓冲），每次重连都停在同一位置，看起来像"模块发了 512 字节就不发了"。
- **排查推导**：一度怀疑模块坏、供电不足，换线、换充电宝、降波特率都没用。最后回头看超时分支，发现清了 `app_ota_staged` 却**忘了清 `ota_last_staged`**：
  ```c
  app_ota_staged = 0;        // 清了
  // ota_last_staged 没清 ← 就是这个
  ```
  下一轮第一包到达时 `app_ota_staged(512) == ota_last_staged(512)`，判定"数据没有增长"，于是不刷新时间戳，直接用上一轮的旧时间戳判超时 → 立刻报"已收 512" → 断线重连 → 无限循环。
- **解决**：超时分支里同时清零 `ota_last_staged`；更彻底的做法是放弃"看门狗"，改成停等 ACK 协议。
- **复盘总结**：**硬件故障是随机的，软件 bug 才是"整齐"的**。现象稳定停在同一个数值时，先怀疑自己的状态机，而不是先换硬件。

### 6. 读回来全是 `00`：W25Q64 根本没应答
- **现象**：修完上一条后仍然"包头不对"。加 12 字节诊断打印后：`staged=17048 rx_total=17048 lost=0 uart_err=0 包头=00 00 00 00 00 00 00 00 00 00 00 00` —— 接收字节数完全正确、一个都没丢，但读回全 0。
- **排查推导**：`00` 既不是擦除态（`FF`），也不是丢开头（乱码），而是 SPI 读回时 MISO 没有数据 —— **W25Q64 没在应答**，属于接线/供电问题。
- **解决**：检查 W25Q64 的 3.3V / GND / CS / CLK / MISO / MOSI，接好后读回正常。
- **复盘总结**：把"读回来是什么"做成一张对照表，排查效率会高很多：
  | 读回内容 | 含义 |
  |---|---|
  | `FF` | 没写进 Flash（擦除后没写 / 写失败） |
  | 乱码 | 丢开头（时序问题） |
  | `00` | Flash 没应答（SPI/供电） |
  | `OTA1` | 数据其实是好的，问题在别处 |

## 硬件与工具链

- **MCU**：STM32F103C8T6（Cortex-M3，64KB Flash / 20KB RAM，HSE 8MHz × 9 = 72MHz）
- **外部 Flash**：W25Q64（SPI），12 个扇区做固件暂存
- **Wi-Fi**：ESP8266（AT 指令，USART3，115200）
- **开发环境**：Keil MDK（ARMCC 5.06）
- **自制工具**：
  - `make_ota.exe`：用 C 重写的打包工具（替代 Python 脚本），输出与 `zlib.crc32` 完全一致，已用 SHA256 逐字节比对；“**编译后自动打包**”挂在 Keil 的 After-Build 里。
  - `send_ota.ps1`：电脑端 Wi-Fi 发送工具，实现停等 ACK、断点续传、端口占用自检。

## 项目结构

```
├── Bootloader/                  # 0x08000000，20KB
│   ├── APP/OTA.c                # 接收 / 校验 / 搬运 / 跳转
│   └── user/main.c              # 上电判断：有标志→搬运；有请求→接收；否则跳 APP
└── APP/                         # 0x08005000，最多 40KB
    ├── Core/Src/esp8266.c       # AT 指令驱动（IT + 循环 DMA 双阶段）
    ├── Core/Src/net.c           # Wi-Fi OTA 协议（CHUNK/ACK/断点续传）
    └── MDK-ARM/                 # 工程 + 打包/发送工具
```
